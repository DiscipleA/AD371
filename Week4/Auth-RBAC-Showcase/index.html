01

Problem & Scope

A hidden button is not a security boundary.

Identity is only the beginning

A browser can change its own HTML, requests, and local state. Signing in must not let a visitor claim an administrator role or bypass a protected endpoint.

Put the decision on the server

Supabase Auth manages credentials. Our Edge Function and SQL guard check the current identity, session, and owner-assigned role before returning protected data.

Small, intentional scope. Register, log in, log out, and request Public, User, or Admin resources. New accounts receive User access only. There is no admin signup, role editor, or sensitive production dataset.

02

Architecture Concepts

Six ideas behind one permission decision.

AuthN · identity

Who is making the request?

Supabase Auth checks email and password, manages verification, and issues the session. The page does not verify passwords itself.

Salted bcrypt · delegated

Hash, never store plaintext

Supabase Auth owns salted bcrypt password hashing. This app sends credentials to Auth over HTTPS; it neither implements hashing nor reads stored hashes.

JWT · short-lived proof

A session is not a role

A signed access token identifies the caller. Keep the session in page memory only; a token's presence is not proof that access is allowed.

AuthZ · server policy

What may this caller do?

Our Edge / SQL RPC boundary checks identity and active session. Admin requests also require a current role from the private roles table.

Ownership · least privilege

No self-promotion

Trusted database administration assigns roles. Signup fields, user metadata, and browser controls cannot grant Admin access.

200 / 401 / 403

Make denial observable

Success returns permitted data. A missing or invalid session is 401; an authenticated User at the Admin boundary is 403. A failed dependency is not success.

03

System Architecture

Two journeys. One server-owned security boundary.

First establish who the caller is. Then decide what that caller may access. The static frontend never owns either decision.

200 Allowed
Public, or all protected checks pass.
401 Authenticate
Missing, invalid or absent server session.
403 Forbidden
Signed-in User requesting Admin.
503 Fail closed
Authority or safe response unavailable.
Read the request path and trust contract

A · Identity is managed

1–2 · Browser ↔ Supabase Auth. Registration and login send email/password directly to Auth over HTTPS. Auth owns salted bcrypt hashing, email confirmation and session issuance. Our page keeps the access/refresh session in memory; it neither stores password hashes nor imports a session from callback URLs.

B · Edge / RPC guard: permission is application-owned

  1. Browser → Gatekeeper: GET ?resource=public|user|admin. Exact origin, method and resource validation run first. Public returns without calling Auth or SQL; a publishable key is configuration, not Admin authority.
  2. Gatekeeper → Auth: protected requests require a Bearer token. The handler calls /auth/v1/user to verify the caller; decoding a JWT alone is not authentication.
  3. Gatekeeper → PostgREST → SQL: the same caller JWT reaches gatekeeper_resource. PostgREST validates it; only the authenticated API role may execute the RPC. The request never supplies a trusted user ID or Admin role.
  4. SQL → trusted data: check auth.uid() and ownership of the matching auth.sessions record, then read gatekeeper_private.user_roles. No role row means User; only Admin may read admin_briefing. Private roles table grants deny browser access. The narrow security-definer function has an empty search path and a privileged, trusted owner.
  5. Decision → Edge → browser: SQL returns an internal status/body envelope. Edge maps it to actual HTTP, validates safe fields and omits credentials. A direct RPC may return HTTP 200 with a denial inside its envelope; that is not permission to access the resource.

C · Lifecycle and failure stay explicit

Logout clears page credentials and requests current-session revocation. The SQL session-row guard is designed to reject a revoked session; copied-token replay remains a separate verification check. Role changes are read on the next request, not trusted from browser metadata. If Auth, the role lookup or response validation fails, protected data is not released. CORS is an origin rule—not authorization.

Build Gatekeeper Lab as standalone HTML, CSS, and vanilla JS.

1. Preserve the seven-section presentation, local navigation,
   seven installed theme packages, and independent light/dark
   mode. Use local appearance keys gk-style-theme and gk-theme.
   Do not copy the reference cloud-theme feature or alter it.

2. Use locally vendored Supabase JS for Auth. Register with
   email and password, require email verification, and keep
   registration to at least 12 characters and at most 72 UTF-8
   bytes. Login must accept existing valid credentials without
   imposing the new-registration minimum. Hashing is delegated
   to Supabase Auth's salted bcrypt, not browser code.

3. Disable session persistence and URL session detection.
   Keep access/refresh tokens only in page memory; reloading
   signs out locally. Never save passwords or expose tokens
   in HTML, logs, URLs, or the response inspector. Use only a
   publishable browser key, never server secrets.

4. Implement our gatekeeper Edge Function for public, user,
   and admin resources. Validate the caller with Supabase Auth.
   Invoke a narrow SQL RPC using the caller's identity. SQL
   independently checks identity, an active auth session,
   and the current role from a private owner-managed table.
   New accounts are Users; metadata cannot grant Admin.
   Revoke browser access to role tables. Restrict RPC grants,
   use an empty definer search_path and qualified SQL names.

5. Return genuine status and allowed JSON: Public can succeed
   without login; protected resources require an active session
   (401), and Admin additionally requires Admin role (403).
   Fail closed on dependency failures. Use strict resource
   validation, no-store responses, and an exact CORS allowlist;
   CORS does not replace identity or permission checks.

   and Log in actions, logout, signed-out and role displays,
   and Public/User/Admin request buttons. No role dropdown.
   Disable network controls until configured. Show the selected
   endpoint, actual HTTP result, and safe JSON, not pretend
   success badges. Reject stale concurrent results and clear
   protected output on session change. Use generic login errors.

7. Write tests first. Check positive and negative AuthN/AuthZ,
   hostile input, byte limits, forged roles, expiry, direct RPC,
   logout replay, races, offline failures, secret redaction,
   keyboard access, themes, and mobile layouts. Separate local
   controlled tests from observed live responses and pending
   checks. No account changes, deployment, or Git actions
   without separate approval of the exact target.
05

Audit

A design contract to inspect—not a claim of a completed live security audit.

Permission contract · explanatory excerpt
PUBLIC  → no sign-in required
USER    → verified identity + active session
ADMIN   → verified identity + active session
          + owner-assigned Admin role

Missing / invalid / revoked session → 401
Authenticated User requesting Admin → 403
Unavailable authority or role lookup → fail closed

Browser input and user metadata never grant a role.
Supabase Auth owns password verification and bcrypt.
Our Edge / SQL guard owns application authorization.

Check the authority

Enforce the same boundary in SQL, not only in the interface or Edge route. Keep role writes under trusted ownership.

Check session lifecycle

Use memory-only tokens. Test expiry, logout revocation, replay, and stale responses; do not assume a cleared screen revokes access.

Check data handling

Validate email, password byte limits, and resource names. Return only allowed JSON—never credentials, tokens, or hashes.

Check the evidence

A diagram and a passing local test are not a live permission check. Read the actual HTTP response and state what remains untested.

07

Verification

A checklist to execute against a connected backend—not recorded results.

  1. Start signed out. Request Public, then User and Admin. Compare the actual response with each endpoint's intended permission.
  2. Exercise identity. Try invalid input and incorrect credentials. Register a test account, verify its email, and log in.
  3. Exercise roles. A User may request User data, not Admin data. Test Admin only with a separately provisioned test account.
  4. End the session. Log out, retry protected access, and test token replay separately. Reload to confirm local sign-out.
  5. Challenge the boundary. Check direct RPC, altered metadata, expiry, and unavailable services without exposing tokens or secrets.
  6. Use the interface. Tab through fields, buttons, prompts, and menus. Try all seven themes, both modes, and a narrow screen.

Identity is managed. Authorization is enforced. Confidence comes from real requests—including the ones the server refuses.
