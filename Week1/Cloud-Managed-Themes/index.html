01

A static application, with cloud-managed defaults

Add a data service without rebuilding the website or depending on the network to render.

Before: settings in source code

The original portfolio supplied seven theme packages and an independent light/dark setting; this standalone companion retains those renderers. Changing the site-wide default or menu order previously required a source edit and deployment.

After: one public settings record

Supabase stores the default theme, mode, and menu order. A static HTTP host delivers this standalone application. The browser validates configuration and reuses the existing theme controller.

Actors & non-goals. The site owner manages public defaults; visitors choose their own appearance. This prototype reads configuration only. It does not add visitor accounts, an administration screen, remote theme-code delivery, or a new hosting layer.

Text equivalent: ownership, flows & fallback

Three execution and trust boundaries, not a trace of a live request:

  1. Static host → Browser: Static HTML, CSS, JavaScript, and local theme packages are delivered to the Visitor Browser. Static host does not proxy this configuration API or access PostgreSQL.
  2. Browser → API: The browser sends a direct HTTPS GET with a publishable key to the Supabase Data API / PostgREST. API → Browser: The response is configuration JSON, not executable JavaScript, CSS, or arbitrary asset paths.
  3. Database boundary: PostgreSQL persists public.portfolio_theme_settings. SELECT operation grants and an RLS SELECT policy allow the portfolio row to be read. INSERT, UPDATE, and DELETE are denied for browser roles; administrative edits remain possible. RLS does not replace operation grants.
  4. Normal preference input: The browser validates default_theme, default_mode, and theme_order against its local whitelist. Saved preferences in localStorage and current-page choices are inputs even after a successful GET. Style and mode are independent; only explicit dimensions override configured defaults. Blocked storage leaves memory-only preferences for the current page session.
  5. Failure path: A validated configuration cache is localStorage-backed when available. Failed or timed-out reads use that cache, otherwise bundled defaults shipped in code—not preferences storage. Newer requests supersede older work; current choices are resolved after asynchronous loading.
  6. Local rendering: The existing controller activates available local packages. A successful API read does not prove every CSS or visual asset loaded. Bounded waiting and fallback reduce the dependency; they cannot guarantee API availability or complete asset rendering.

Implementation specification · AI build prompt
Suggested implementation prompt
Add read-only cloud configuration to this static
application without replacing its local rendering
system.

1. Preserve local rendering. Theme packages and
   standalone navigation remain usable independently
   of the configuration request. Do not add other
   portfolio pages.

2. Verify the architecture. PostgreSQL stores one
   public settings record; the Supabase Data API
   exposes permitted reads through PostgREST. The
   record controls the default theme, color mode,
   and menu order, not CSS or assets.

3. Restrict access. Use a publishable browser key
   with SELECT grants and a row-level SELECT policy.
   Browser roles cannot insert, update, or delete
   settings. Keep database passwords and privileged
   keys out of the frontend.

4. Reuse the renderer. Validate remote values
   against installed local theme IDs. The shared
   theme controller applies local CSS and assets;
   remote configuration cannot execute code or
   supply arbitrary asset paths.

5. Handle failure and preferences. Render
   immediately. Use validated cache or bundled
   settings when a request fails. Override defaults
   only in dimensions the visitor explicitly
   selects, including choices made while requests or
   metadata loads are pending. Save choices when
   browser storage is available; otherwise keep them
   for the current page session.

6. Verify observable behavior. Show actual request
   status, duration, and returned settings. Label
   offline simulation. Exercise reads, permission
   checks, independent preferences, malformed data,
   failure recovery, keyboard access, responsive
   layouts, and Chromium/Firefox behavior. Keep
   executed results separate from explanatory
   diagrams and pending deployment checks.

07

Verification

Try the feature, inspect the evidence, and refine only what fails.

  1. Reload and compare the configured default with the current appearance.
  2. Choose a style and mode; check persistence and reset behavior.
  3. Try offline simulation and confirm the fallback source.
  4. Test search, Tab, Enter, and visible focus.
  5. Check all installed themes at desktop and mobile widths.

Cloud settings choose defaults; local packages render the result. The useful trade-off is flexibility without handing rendering ownership to the backend.
