01

Problem & Scope

A working storefront should not depend on one backend.

One action, a real boundary

A product card alone cannot show where a request runs. Ask the server for a sneaker quote, then inspect which replica answered—without letting the browser contact a backend directly.

Two interchangeable replicas

The local Docker design places one Nginx gateway in two bridge networks. Two copies of the same Node API remain private. Either copy can calculate the same quote without a session or database.

Small, intentional scope. One product, quantity 1–9, a server-calculated quote, a short request trail, and explicit health checks. This is a read-only network lab—not checkout, payment processing, or an order service.

Architecture Concepts

Six ideas behind a request that can reach either server.

Bridge · membership

Separate who can connect

User-defined bridges connect containers on the same network. This lab gives the gateway a public-side bridge while keeping both APIs on a separate private bridge.

Docker · Bridge networks ↗ Internal · limited reach

Keep the backends private

The private network uses internal: true. Neither backend publishes a host port. This limits container network reach; it does not remove the Docker host's privileges.

Docker · Internal networks ↗ DNS · service names

Find a service, not an IP

The proxy addresses store-a and store-b by Compose service name. Container addresses can change after recreation, so DNS refresh and recovery need explicit verification.

Docker · Service discovery ↗ Round-robin · equal peers

Distribute the same work

Nginx uses round-robin by default for an equal-weight upstream. Both replicas serve the same API; request counts show observed distribution, not a promise of perfect alternation.

Nginx · HTTP load balancing ↗ Retry · bounded failure

Try another eligible peer

Selected upstream failures can retry a read-only GET before a response is sent. Retry count and time must be bounded; a failed dependency must never become a fabricated quote.

Nginx · Proxy retry policy ↗ Health · a separate signal

Check each replica directly

Compose health checks test container readiness. The page's pinned health routes observe each API separately; Compose health alone does not configure Nginx's runtime peer selection.

03

System Architecture

One entry point. Two networks. Two copies of one API.

Read this as the local Compose design contract. The browser runs React outside the containers. Nginx is the only dual-homed service; both replicas belong exclusively to the internal network.

Read the request path and ownership contract

1 · Browser → gateway

React runs in the host's browser, not in a backend container. The local Docker build serves compiled HTML, CSS, and JavaScript from Nginx; an API GET returns to the same gateway. public_subnet names the public-side bridge, not a cloud subnet or a promise of Internet access. Host port 80 is loopback-bound by default.

2 · Gateway → one private replica

Nginx alone joins both bridges. Its upstream resolves store-a and store-b using Docker service discovery, rather than hard-coded container IPs. Both replicas run the same image, validate quantity, and calculate the same integer-cent total. There is no server-side cart, shared session, or database. The browser's quantity and request trail last only in the current page.

3 · Replica → gateway → browser

The selected API returns a safe server identifier and calculated quote. Nginx forwards the response; the browser validates it before updating the order summary and counts. A last response is an observation, not proof that a replica is still healthy. Health requests use separate pinned routes so one replica cannot answer for the other.

Failure, isolation, and hosting limits

Retries apply only to configured upstream failures, within a finite try/time budget and before output is sent to the client. A failed or malformed reply stays a failure. Compose health checks and Nginx peer failure handling are separate mechanisms. Bridge isolation does not exclude host privileges or a Docker administrator, and does not make these replicas independent machines.

A separately hosted static page is a future option, not a deployed service here. It would need an explicitly configured, reachable HTTPS API endpoint and matching origin policy. Merely publishing the page cannot start containers or reach a visitor's loopback lab.

Build a standalone StyleStore Network Lab, not a simulation.

1. Preserve the seven-section App Engineering showcase,
   local navigation, seven theme packages, and light/dark
   appearance. Adapt copied storefront components into a
   React island mounted only at #stylestore-root. Do not
   edit the source portfolio or load a cloud theme service.

2. Use Docker Compose with two distinct bridge networks:
   public_subnet and private_subnet. Set the private network
   internal: true. Only Nginx joins both. Publish Nginx host
   port 80 on loopback by default. Never publish API ports.

3. Run store-a and store-b from the same Node image and API
   code, differing only in a safe server identifier. Attach
   them only to private_subnet. Use service-name discovery,
   supported DNS refresh, and equal-weight round-robin.
   Use explicit timeouts, buffering, and bounded GET retries.

4. Serve one product: retro-sneakers, Retro Sneakers,
   8500 USD cents. GET /api/quote?quantity=N accepts one
   integer quantity from 1 through 9 and returns serverId,
   product, quantity, totalCents, and currency. Calculate
   totals on the server. Reject malformed, duplicate, and
   unknown query fields. No checkout, payment, or storage.

5. Implement /healthz for each API and separately pinned
   /api/health/store-a and /api/health/store-b proxy routes.
   Do not fail over pinned health checks. Add the gateway
   response marker X-Lab-Gateway: nginx. Keep Compose health
   distinct from proxy peer selection and browser evidence.

6. Provide quantity, a quote action, 10 serial real quotes,
   explicit health checks, Clear, and a compact monitor.
   Use public config.js with an empty apiBase for same-origin
   requests; allow a future explicitly configured HTTPS API.
   Validate gateway marker, safe IDs, requested quantity,
   integer-cent totals, and response shape. Bound waits and
   response size; omit credentials and bypass caches.

7. Show idle, busy, success, invalid input, unavailable,
   and malformed-response states honestly. Count only valid
   successful quotes, track failures separately, and keep
   health observations independent. Clear must abort work
   and reject stale results. Never invent fallback replies.
   Keep controls labeled and keyboard/mobile accessible.

   private-network isolation, only one published entry,

   tests, and limitations within the approved file scope.

Audit

A design and code review contract—not completed runtime results.

Network contract · design excerpt, not full config
nginx:
  networks: [public_subnet, private_subnet]
  ports: ["127.0.0.1:80:80"]

store-a, store-b:
  image: same application image
  networks: [private_subnet]
  ports: none

private_subnet:
  driver: bridge
  internal: true

upstream: service names, equal weights
retry: explicit conditions + finite tries/time
health: pinned per replica, never balanced

Ports · one published entry

Inspect normalized Compose and running bindings. Only Nginx publishes a port; neither backend gets a host mapping.

Network membership · exact peers

Inspect both networks. Nginx alone joins both; each API joins only the internal private bridge. Test public-only isolation separately.

DNS / retry · recovery is explicit

Review service-name resolution, refresh, timeouts, and retry limits. Recreate a service; do not infer DNS recovery from a startup success.

Stateless balancing · same API

Compare image and API contracts. Observe valid quote IDs over a batch; test one stopped replica and its restoration without claiming perfect alternation.

Working System

Choose a quantity. Request a quote. See which server answered.

One product, one read-only quote—not a purchase. When connected to the running lab, every quote, batch item, and health check makes a real request. An unavailable API remains unavailable; there are no synthetic fallback responses.

07

Verification

Try these checks against a running lab—not a list of claimed passes.

  1. Request a quote. Choose a quantity from 1–9. Compare the returned quantity and server-calculated total with the order summary and responding replica.
  2. Run a batch. Send ten actual quote requests. Inspect the successful counts and failures; healthy distribution need not alternate perfectly.
  3. Check health separately. Request both pinned health routes. Compare their individual observations with the quote trail; a previous response is not current health.
  4. Use an operator-controlled failure. With local operator access, stop one replica, request quotes, restore it, and verify recovery. The page cannot stop containers; never leave a stopped replica unattended.
  5. Challenge the boundary. Inspect ports and network membership, check public-only isolation and service recreation, try invalid input, then test an unavailable API. Host privileges remain outside bridge isolation.
  6. Use keyboard and mobile. Tab through navigation, theme controls, links, prompts, and storefront actions. Try all themes, both modes, a narrow mobile screen, and the diagram's layout change.

The map explains the contract. Actual responses, container inspection, and deliberate recovery checks establish what the local lab does.
