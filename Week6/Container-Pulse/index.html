Problem & Scope

A container that starts is only the beginning.

From CSS composition to application

The asymmetric dashboard supplies the visual hierarchy. Container-relative notification cards supply the feed. React connects both to a small runtime API instead of placeholder metrics and example alerts.

From one image to multiple instances

A multi-stage build separates frontend tooling from the runtime. Compose starts replicas with non-root execution, explicit resource budgets, health checks, and restart policies. A gateway gives the browser one stable address.

Small by design. Check runtime metadata, sample several requests, and acknowledge observed notifications. There is no database, login, remote administration, or claim of multi-host high availability.

System Architecture

Build one image. Run constrained copies. Trace where every observation comes from.

Build, lifecycle & observation ownership

Build artifacts: the pinned Node Alpine build stage installs the lockfile-defined dependencies before application source, then compiles React. The final Alpine stage copies only dist and server, declares USER node and configures health checking. Build-stage tooling is not an application runtime dependency.

Containers, not network topology: Compose consumes the image and .env settings to create two equivalent instances, scalable to three and back. Each application container has its own Node process, static assets and metadata/health handlers, with 0.50 CPU and 128 MiB ceilings, a read-only filesystem and dropped capabilities. These are configured resource limits, not measured CPU or memory use.

Lifecycle: Docker runs each app's local /healthz probe every five seconds with a three-second timeout. Health state and the unless-stopped process-exit restart policy are separate: a merely unhealthy container is not automatically restarted by that policy. Trusted operator commands build, inspect and scale; browser visitors cannot administer Docker.

Supporting gateway: Nginx routes HTTP to interchangeable application processes. Its own container runs non-root with a 0.25 CPU / 64 MiB budget. This lab uses one dedicated project network; the public/private subnet design belongs to the earlier networking showcase.

Observation provenance: hostname, process uptime and versions come from the responding Node process. HTTP outcome and request duration are measured by the browser. The latest twelve completed observations feed the graph and gauges; per-host shares use validated responses only. Cumulative successful checks and encountered identities describe the current page, not a complete replica inventory or a cluster-health verdict. Clear cancels pending work and resets browser observations.

Reading the map: this is one fixed SVG composition. At narrow widths the entire map, including labels and arrows, scales down together without changing its topology. This expandable explanation remains available as its text equivalent. Static portfolio publication alone cannot run these containers; the API still needs running compute.

7. Health and lifecycle. Dockerfile and Compose app probes run node server/healthcheck.mjs with 5s interval, 3s timeout, 5s start period and 6 retries. The Node probe connects to 127.0.0.1 at PORT (default 3000), GET /healthz, agent: false, timeout 2000 ms; reject bodies longer than 1024 characters and require HTTP 200 with exactly two JSON keys, status "ok" and service "container-pulse". Gateway health uses wget -q -T 2 -O - http://127.0.0.1:8080/healthz piped to grep for "status":"ok", with the same Compose interval/timeout/start/retry settings. Gateway health demonstrates a proxied response, not every replica's health. Health state and process-exit restart policy are distinct: unhealthy status alone does not restart a still-running process. Handle SIGTERM/SIGINT gracefully in the server: stop accepting work, close idle connections, then force remaining connections closed and exit 1 after 5000 ms if shutdown cannot finish.

8. Non-secret configuration. Supply .env.example literally as HOST_PORT=8796, REPLICAS=2 and APP_VERSION=1.0.0 on separate lines; README setup uses cp .env.example .env. Never read or publish a private .env to generate documentation. HOST_PORT and REPLICAS configure Compose interpolation; APP_VERSION reaches the Node process through app env_file. Compose explicitly fixes app PORT=3000 and NODE_ENV=production. The standalone server and health probe accept PORT matching /^\d{1,5}$/ with numeric value <=65535 (0 is allowed for an ephemeral test port); invalid configuration exits with a sanitized failure. Server APP_VERSION defaults/falls back to 1.0.0 unless it matches /^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$/. Frontend config.js is window.ContainerPulseConfig = Object.freeze({ apiBase: '' }); default requests are same-origin. An empty or slash-prefixed apiBase preserves same-origin transport; safe paths match /^\/(?:[A-Za-z0-9._-]+\/?)*$/ without '.' or '..' segments. 9. Exact public JSON APIs. GET /healthz returns HTTP 200, application/json; charset=utf-8 and exactly {"status":"ok","service":"container-pulse"}. GET /api/runtime returns HTTP 200 with exactly five fields: service: "container-pulse" (literal string); hostname: string from os.hostname(); processUptimeSeconds: number from process.uptime(); nodeVersion: string from process.version; appVersion: string from the validated configured version. Do not add environment dumps, limits, container IDs, CPU/RAM measurements or invented telemetry to this API. Describe process uptime, not container uptime; the displayed capture does not tick between requests. GET / and /index.html return the built showcase. Each replica implements all these endpoints; the gateway routes them without substituting fake successful responses.

10. HTTP and static-serving boundary. Accept GET and HEAD only; HEAD retains the applicable status, Content-Type and Content-Length but sends no body. Other methods, including the explicit CONNECT handler, receive 405 {"error":"Method not allowed"}, Allow: GET, HEAD; CONNECT closes its detached socket. Validate raw request targets before normalization: start with a single '/', maximum 2048 characters, no percent encoding, query delimiter (even empty '?'), fragment delimiter, backslash, control/space/DEL characters or '.'/'..' path segments. Reject these with 400 {"error":"Bad request"}. Unknown or missing public files return 404 {"error":"Not found"}; unexpected handler errors return 500 {"error":"Internal server error"} without filesystem/environment details. Malformed HTTP parsing returns sanitized 400 with an empty body and closed connection. Keep maxHeaderSize 8192, requestTimeout/headersTimeout 10000 ms and keepAliveTimeout 5000 ms. Allowlist index.html, theme.js, site-navigation.js, copy-code.js, config.js, the existing shared/showcase/dashboard styles, theme-registry.js, the seven known theme packages and their approved SVG assets. /assets/ filenames must start alphanumeric, use only alphanumeric/underscore/hyphen and an approved js/css/svg/png/jpg/jpeg/webp/ico/woff2 extension, without nesting. Use MIME types from server/server.mjs; require realpath containment, O_NOFOLLOW and a regular file to prevent symlink escape. No dotfiles, maps, package files, arbitrary styles/scripts, no directory listing and no SPA fallback.

Verification

Try the small flow. Inspect the infrastructure separately.

  1. Request: check runtime and inspect the hostname, process uptime, versions, actual HTTP outcome, and measured duration.
  2. Observe: sample several requests and compare the notification feed with the observed identities. Sampling is not a complete replica inventory.
  3. Acknowledge: use the card's native checkbox. The notification changes presentation without an administrative request.
  4. Reset: clear while idle or pending. Old responses must not restore cleared observations.
  5. Recover: a failed request must report failure, not substitute sample data. Retry after connectivity returns.
  6. Adapt: try themes, light/dark mode, narrow widths, keyboard navigation, and the copyable prompts.
